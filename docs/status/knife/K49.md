# K49: a frame larger than the texture cache froze the game (issue #13)

Package K49, 2026-11-11, version **0.1.8**. No game data was added.

## 1. The report

Issue #13: the game froze on one picture in `03_00_ARC03_5B` (script 70, flowchart node 356) and nothing got past it. The reporter's files were fine.

## 2. Cause

The texture cache cap follows the card's dedicated memory: a third of it, between 512 and 1536 MiB (`VideoMemory.CacheCapacity`). On Windows a card with
1.5 GB or less, which includes most integrated graphics, gets 512 MiB; Linux and macOS do not read the card's memory and always get 1536 MiB, so only Windows
froze this way. One frame of that scene draws 566 MiB of picture tiles. The LRU cache evicted the frame's first tiles
with its last uploads, so the frame was never complete, and in real play a frame whose textures are not all resident is not drawn: the picture before it stayed
on the screen for ever. It is not one scene: 22 scripts have a frame above 512 MiB, the largest 798 MiB (script 464).

Verification runs never saw it: they ran on a 16 GB card (1536 MiB cap), and the hidden runs that take screenshots do not hold frames.

## 3. Fix

- `TextureCache`: the textures the frame being prepared draws are pinned (`BeginFrame`, `Pin`) and never evicted. The cache stays above its cap for such a
  frame and trims (`TrimUnpinned`) once nothing draws them.
- `TextureFeeder`: names every texture of the frame before anything is uploaded; no look-ahead while the frame fills the cache; a tile whose decode threw is
  not waited for. `UploadScheduler.Uploaded` keeps the feeder's queued set exact.
- `GameApp` / `TextureHold`: the hold for textures has an end: 1 s with nothing in flight, 8 s otherwise, counted in passes of the loop. The frame is then drawn
  with what is resident and the log says so, so a damaged game file cannot freeze the game either.
- `DecodeWorkers`: a job being picked up counts as pending.
- `TSUKI_TEXTURE_CACHE_MIB` (64..8192): a verification run can ask for a smaller card's cache.

## 4. Verification

| check | result |
|---|---|
| Before the fix, 512 MiB cap, tour to node 356 in hold mode | stuck at step 6540 for minutes, on the picture of the report |
| After the fix, same run | plays through; the log names the 566 MiB frame |
| Whole flowchart at 512 MiB in hold mode | 495 of 495 nodes started, no stall, no given-up hold; 22 scripts above the cap |
| The 23 over-cap nodes at 128 MiB | all pass |
| 1536 MiB cap, before against after | same log lines; no new or longer hitch |
| A damaged tile (one overwritten tile stream in a test copy) | v0.1.7 froze at it; now the log names it and the game plays on |
| Linux build in WSL at 512 MiB | passes the scene with the same over-cap line |
| New tests | cache and scheduler (13), decode failures (2), the hold's rules and their wiring, the feeder and the real scene with the game; each fails without its fix |

Not verified: a real card with 1.5 GB or less. The cache was forced to 512 MiB on a 16 GB card, so what a small card's driver does with 800 MiB of
textures was not seen. About half the tiles of the largest frame are outside the picture; not drawing them would shrink such frames (not done here).
